一、场景应用
注意：Redis没有回滚也没有重试，一个内存数据库没有这么复杂的功能
1、在高并发秒杀场景下，使用Lua脚本通过EVAL命令在Redis服务端原子执行，能确保“检查库存并扣减”和“记录用户购买明细”作为整体操作一次性完成。避免了网络往返，
仅使用依次EVAL调用，且在服务端保证原子性，显著提升成功率。
2、CROSSLOT错误
  CROSSLOT Keys in request don't hash to the same slot，当你在一个开启了集群模式的Redis集群上，尝试一个设计多个Key的操作，比如同时获取两个不同的Key，
而这些Key并不属于同一哈希槽时，Redis就会报这个错。
  为什么会出现这个问题？
  为了保证数据一致性，Redis集群要求某些多key操作必须在同一个哈希槽内进行，否则就可能出现逻辑错误。
  如何解决？
  最常用的方法就是使用哈希标签Hash Tags，在创建Key的时候，加上大括号{}，强制让相关的key共享同一个标签，这样它们就会被分配到同一个哈希槽里，多key操作就能顺利执行了。
在Redis Cluster中需要对两个相关key执行多键操作，如Lua脚本中的读改写，避免出现CROSSLOT错误并获得原子性，可以通过哈希标签将相关key放入同一槽位，例如user:{42}:a 和 user:{42}:b,来避免这个问题。
Redis Cluster要求多键操作的所有键必须位于同一个槽位以避免CROSSLOT错误，CRC16 规则 通过对{}中的数值进行哈希计算，得到最终槽位结果，如果不加{}，那么还是按照整个字符串进行哈希值计算，不能保证在同一个槽位中。

3、Zset底层的存储结构包括ziplist和skiplist，在同时满足有序集合保存的元素数量小于128个和有序集合保存的所有元素的长度小于64字节的时候使用Ziplist，其他时候使用skiplist

4、当需要在Redis中高效存储用户会话数据Session ID 及其元数据，并支持快速读写单个字段，应该是使用Hash结构。

5、在Redis持久化策略中，AOF模式通过记录每个写操作命令到日志文件中，支持更细粒度的数据恢复，如每秒同步或者每次操作同步，从而提高更高的数据完整性和一致性保证，
尤其在高耐久性配置下减少数据丢失的风险。相比之下，RDB模式使用快照机制，可能会导致最后依次快照后的数据丢失。AOF占用磁盘大小通常比RDB模式要大，AOF数据恢复
需要重放所有命令，速度较慢。AOF在高耐久性模式下，如appendfsync always会增加写入操作延迟，而RDB的写入延迟通常比较低。

6、Redis集群采用哈希槽机制分布key到不同节点以实现水平扩展。Key通过CRC16 哈希算法映射到16384个固定哈希槽中的一个，槽被动态分配到集群节点上，从而支持通过添加或者移除节点来水平扩展。
7、Redis的默认内存淘汰策略是‘Noeviction’会在内存不足时拒绝所有写操作，只允许读操作
8、Redis的Pipelining指数要用于减少网络往返延迟TRR，但是不能保证原子性；事务MULTI/EXEC通过将命令打包执行来保证在执行期间不被其他客户端命令插入，提供隔离性，但是不提供回滚机制。
9、在实现分布式锁的时候，Redis使用SETNX命令与过期时间组合可以防止多个客户端同时获取锁。SETNX命令通过与过期时间组合是Redis实现分布式锁的标准机制，它通过原子性地设置键值仅在键不存在时候成功，
并结合过期时间防止死锁，从而确保只有一个客户端能获取锁。
WATCH用于监视键变换的乐观锁而非独占锁
10、在Redis集群模式下，节点使用哈希槽机制进行数据分片。当客户端访问的键不再当前节点时，节点会通过返回MOVED响应来指示客户端重定向到拥有改键槽的正确节点，MOVED响应包含正确节点的地址信息。
11、线上实例同时开启了RDB快照和AOF。实例发生宕机后重启，Redis默认会优先使用哪种持久化方式来恢复内存状态？若AOF开启则优先加载AOF文件。
12、在Redis中，Lua脚本的执行机制保证了多命令的原子性，Lua脚本默认在Redis主线程（单线程模型）中执行，整个脚本作为一个原子操作运行，不会被其他命令中断，从而优化多命令原子执行。
Redis的Lua脚本只支持同步执行，客户端必须等待脚本执行完毕并直接处理结果，不支持异步和回调机制。
13、Redis集群搭建当数据库中的16384个槽位都分配对了节点时，集群处于上线状态，集群配置文件由Redis节点维护，集群中指定主从关系使用cluster replicate命令，各节点在启动节点阶段是独立的，没有建立联系。

14、Redis支持的HyperLogLog数据类型，应用场景包括统计网站的UV独立访客，应用HyperLogLog数据类型时可能存在一定的错误率，HyperLogLog数据类型占用内存是固定的。

15、在Redis高可用部署中， Sentinel系统通过监控主实例的心跳状态来检测失败，当检测到主实例不可用时，多个Sentinel节点会进行投票以达成共识，并自动触发故障转移过程，将从实例提升为新主实例。

16、Redis内存：通过info memory 可以查看内存使用情况，used_memory_rss代表Redis进程占据操作系统的内存；used_memory中不包含内存碎片；mem_allocator是Redis使用的内存分配器，默认是jemalloc

17、当Redis内存使用达到maxmemory限制并触发淘汰策略时，如果配置的策略是allkeys-lru,Redis会随机采样一部分key，然后从这个样本中淘汰掉最久未被使用的key进行淘汰。
18、在Redis Sentinel机制种，当一个Sentinel节点主观认为master节点已下线后，它会向其他Sentinel节点发送SENTINEL is-master-down-by-addr命令进行询问，以获取其他Sentinel对Master节点状态的判断，
从而收集足够投票将Master标记为客观下线。SENTINEL get-master-addr-by-name用于获取master地址，不涉及下线状态。

19、在Redis主从复制中，从节点首次连接主节点时会触发全量同步；主节点复制积压缓冲区大小不足会导致部分同步失败，从而回退到全量同步；主节点runID变更（如主节点重启或切换）会强制触发全量同步，因为旧runID无效。
从节点发送SLAVEOF用于从节点连接主节点，触发同步类型（全量或部分）取决于复制条件：如果从节点首次连接、复制偏移量不匹配或者复制积压缓冲区不足，会触发全量同步；仅当条件允许时（如偏移量在复制积压缓冲区内）才触发部分同步。
当网络中断导致复制断开后重新连接，如果从节点发送的同步偏移量不在主节点的复制积压缓冲区repl_backlog_buffer范围内，主节点会触发全量同步SYNC。从节点会丢弃本地数据并重新同步所有数据。

20、Redis4.0的混合持久化机制在生成AOF文件时，开头部分是RDB格式的全量数据快照，后续是增量的AOF命令日志。混合持久化不会合并为新的RDB文件，而是生成单一混合格式的AOF文件。恢复数据时 Redis优先使用AOF文件，如果存在，
在混合持久化中加载的是混合格式的AOF文件，而并不是优先使用单独的RDB文件。混合持久化可以在主节点和从节点上通过配置文件开启，不受节点角色限制。

21、RDB文件，RDB文件格式中的check_sum字段用来载入时判断文件是否损坏，RDB文件格式中的db_version字段中记录了RDB文件的版本号；RDB文件的存储路径既可以在启动前配置，也可以通过命令动态设定。
只有当数据库中有键值对时，RDB文件中才会有该数据库的信息。

22、Redis主从复制中，当从节点因网络中断短暂断开后重新连接主节点时，主节点能快速恢复增量数据而非全量同步，主要依赖的是repl_backlog_buffer复制积压缓冲区中的数据。

23、在哨兵集群中，当主节点故障后，新主节点选举完成但客户端仍访问旧的主节点，此时客户端应该实现监听哨兵的状态变更通知来获取最新的访问主节点然后切换连接。

24、在Redis cluster中，当主节点故障时，其从节点通过故障转移晋身为主节点后，会自动继承原主节点的所有SLOT，继续提供服务，无需手动操作或者重新分配槽位。

25、Redis配置文件中，当Redis以includes的方式引入其他配置文件时，如果同一个配置项在不同配置文件中都有定义，以最后面的配置为准。
Redis只支持bytes,不支持bit单位。
在高并发情况下，设置较高的tcp-backlog值以避免TCP的慢连接问题。
Redis支持四级Loglevel：debug、verbose、notice、warning

26、WATCH命令用于监视一个或多个键，如果在事务执行EXEC前这些键被其他客户端修改，EXEC会失败返回nil。
WATCH命令必须在MULTI命令之前执行，不能在之后。
一个客户端的WATCH命令不会直接影响其他客户端的事务执行，它只影响当前客户端的事务，例如其他客户端修改键可能导致当前事务失败。
UNWATCH命令会接触所有被监视键的状态，但这种接触不是永久的，因为客户端后续可以重新调用WATCH命令，进行监视，且在执行EXEC或DISCARD后监视状态也会自动解除。

27、在Redis事务中，当使用MULTI/EXEC命令时，如果某个命令执行失败（例如，语法错误或者对错位类型键进行操作），Redis不会回滚事务，而是忽略该失败命令并
继续执行剩余命令。
如果一个命令在入队阶段（‘EXEC’执行前）就存在语法错误，那么当客户端调用EXEC时，整个事务都将被拒绝执行，并返回错误。

28、Redis数据存储中的redisObject对象，lru记录对象最后一次被命令程序访问的时间，占据的比特数不同的版本不同，4.0版本占24比特，2.6版本占22比特，
type字段表示对象的类型，占4个比特；Encoding表示对象的内部编码，占4个比特；refcount记录的该对象被引用的次数，占4个字节

29、哨兵相关配置：
（1）sentinel failover-timeout用来判断其几个子阶段的超时，
（2）sentinel parallel-sync规定了每次向新的主节点发起复制操作的从节点个数
（3）sentinel down-after-milliseconds对主节点、从节点和哨兵节点的主观下线判定都有效
（4）sentinel monitor指定了主节点名称、主节点地址以及主节点客观下线的哨兵数量阈值

30、缓存击穿是指单个热点key失效时，大量并发请求直接访问数据库的场景。防御的核心策略是使用分布式锁，如Redis的SETNX命令或者红锁算法，确保只有一个线程加载数据到缓存，
其他线程等待或者使用缓存数据，从而避免数据库压力。
31、Redlock算法通过在多个独立的Redis实例上获取锁，解决了在单个Redis实例上使用 SET key Value EX seconds NX 可能因主从复制和故障切换导致锁丢失的问题，从而确保锁的互斥性不被破坏。
32、在Redis分布式锁中，避免因锁持有者崩溃导致死锁的推荐方法是设置锁的过期时间并结合唯一标识检验机制。可以通过持有者标识并在释放时使用Lua脚本进行原子性校验，可确保只有锁的持有者才能释放锁，从而防止误删锁，避免死锁（锁有过期时间作为前提）。
33、缓存击穿 cache breakdown，一个高并发热点key在缓存中过期或失效时，瞬间大量请求直接访问后端存储，引发性能问题。
缓存穿透 cache penetration，是指查询不存在的数据，如无效key。
缓存雪崩 cache avalanche，是指多个缓存key同时失效
34、在Redis主从复制模式下，当从节点首次连接到主节点时，默认数据同步方式是主节点发送全量RDB快照，称为全量同步，用于初始化从节点数据。之后，才通过命令传播进行实时增量同步。
35、在Redis的BGSAVE持久化中，写时复制机制的作用是，当父进程尝试修改数据时，操作系统会复制相应的内存页，即创建副本，使父进程修改副本而不影响子进程正在读取的原始数据页，从而保证子进程保存的RDB快照在BGSAVE开始时的一致性。

二、重定向和槽位处理
1、在Redis集群中，MOVED重定向响应是由于客户端请求的键所对应的槽slot不属于当前节点负责范围时，节点返回的错误，指示客户端连接到正确节点
2、在Redis Cluster进行在线迁移槽位 resharding时，客户端访问被迁移槽位的键可能会收到ASK重定向，该ASK表示临时重定向，客户端需要对目标节点发送一次性ASKING命令，在发送实际操作。
客户端收到ASK重定向表示临时重定向，客户端应向目标节点发送ASKING命令，以启用目标节点在导入槽位时的特殊处理，然后发送实际操作命令。
MOVED重定向表示永久迁移。
3、在集群节点数量变法，如添加或移除节点时，哈希槽迁移需要通过人工干预，例如使用CLUSTER RESHARD 命令，并非完全自动。如果某个节点负责的哈希槽全部不可用，例如节点故障且无副本可用，
集群无法处理针对这些槽位的键操作，客户端会收到错误响应。
